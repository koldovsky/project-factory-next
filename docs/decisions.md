# Design decisions and tradeoffs

These decisions are implemented unless explicitly marked as an external integration. They are engineering choices informed by the [research](research.md), not a claim that this repository has outperformed every factory system.

| Decision | Problem it solves | How it works | Tradeoff / when to change |
|---|---|---|---|
| **1. Portable Node ESM core** | Framework and agent-vendor coupling made the previous process difficult to reason about | One CLI, native process/filesystem APIs, JSON Schema, exact dependency pins | JavaScript is convenient for web verification. A high-volume service may move state/control to another runtime while preserving contracts |
| **2. Structured task contracts** | Markdown keyword heuristics can silently lose verification requirements | Strict schemas plus semantic validation connect every requirement to real check IDs | Authors write explicit contracts instead of relying on inferred obligations; prose remains useful for intent |
| **3. Task profiles** | Different work needs different evidence | Versioned profiles combine instructions with enforced required check kinds and visual constraints | Profiles are policy-bearing inputs, so meaningful changes require a new reviewed digest |
| **4. External control bundles** | A builder can otherwise lower its own acceptance bar | All task policy, evaluator entrypoints and reference inputs live separately; verification requires an externally selected digest | Same-user directory separation is not a sandbox. Production needs separate credentials/mounts/identities |
| **5. Complete content manifests** | Commit-message “approval,” file mtimes and partial locks cannot establish current evidence | Hash every control input and bind runtime/candidate/evidence bytes; refuse silent resealing | Hashes detect drift, not authorship. Authenticate approval and provenance outside the candidate |
| **6. Exact result contracts** | Exit zero, an empty report or a skipped test is not proof | Require a complete nonempty expected case set, affirmative statuses, consistent aggregate and process outcomes | Integrating a test tool requires a proper reporter/adapter; arbitrary console text is not machine acceptance |
| **7. Dependency-ordered checks** | Verification may run before the evidence producer | Validate a DAG, run producers first, mark dependent checks blocked on failure | This is sequential by default. Parallelize only independent checks when it measurably reduces latency |
| **8. Bounded worker attempts** | Unbounded repair can waste time or conceal repeated failure | Task-owned attempt count and per-process deadlines, fresh attempt evidence, explicit terminal failure | A failed task escalates or becomes a new task; it cannot silently extend its own budget |
| **9. Safe native process invocation** | Prompt/finding text can become shell syntax, especially on Windows | Native executables, argument arrays, prompt stdin, bounded output and process-tree cleanup | Shell wrappers are rejected. Use native CLI paths or Node's script entrypoint |
| **10. Local durable state** | A crash must not erase task ownership or pretend incomplete evidence is valid | Atomic JSON replacement, hash-linked history, exclusive run lock, explicit dead-owner recovery | Local disk is not a distributed lease or tamper-proof log. Use a real durable workflow service at multi-host scale |
| **11. Explicit reference creation** | Automatic snapshot updates make a broken candidate its own expected answer | Separate capture/import operations, new directories, reviewed digests, no update-on-failure path | Baseline maintenance is deliberate work. Capture errors must be fixed, not averaged away |
| **12. Visual matrix and multiple signals** | One screenshot can hide responsive and behavioral failures | Every scenario × viewport is checked; compare pixels, landmarks, text, behavior, overflow and automated accessibility | Browser/OS/fonts can change pixels. Use calibrated tolerances and the same environment; static exports have additional rasterization limits |
| **13. Managed static serving** | A supplied URL may serve something other than the candidate | The controller can serve the candidate's selected static directory during acceptance | Dynamic applications need a trusted deployment/source binding; external URLs are explicitly labeled operator-supplied |
| **14. Paired improvement assessment** | A changing task mix can make weak factory changes look successful | Matched task IDs, frozen versions/settings, disjoint splits and predeclared metrics | The assessor requires independently collected data. It does not authenticate JSON records or run a research study by itself |
| **15. Conservative uncertainty and fixed floors** | Tiny samples and tolerated per-generation losses can create false progress | Simultaneous bounded intervals, absolute quality floor, critical-failure rejection; inconclusive is an allowed result | Conservative intervals can require large samples. Redesign the study rather than inventing confidence or lowering policy after seeing results |
| **16. Independent promotion** | A self-improving agent can otherwise optimize its own score and install the result | The assessor emits a proposal; an external authority decides after held-out audit and limited live use | Automated production rollout is an external integration, with explicit rollback and observation contracts |
| **17. Genuine source CI** | Templates and ignored skips do not protect the factory itself | Windows/Linux × Node 22/24, real Chromium, negative fixtures, aggregate required check, SHA-pinned Actions | CI proves tested behavior. Branch/ruleset enforcement and trusted product evaluation remain separate controls |
| **18. One worker by default** | Coordination adds cost and integration failure modes | Sequential implementation and independent evaluation within each run; independent jobs can be launched in separate workspaces | Scheduling and bounding concurrent jobs is an external responsibility. Add specialized reviewers or worker fan-out only after task-family measurements show a gain |
| **19. Preparation before candidate freeze** | A worker can edit source while a stale static export continues passing visual checks | Reviewed sequential build commands run after each worker attempt, with deadlines and input/output digests; only successful preparation reaches serving and acceptance | Declare the correct build explicitly and protect the toolchain. Local ordering does not replace an isolated preparer or authenticated compilation provenance |

## Choices intentionally left configurable

Models, application stack, business requirements, visual scope, reference provenance, time/attempt budgets and evaluator commands vary by task. Configure them before freezing policy. There is no universal “99% similarity means correct” threshold, no blanket permission to deploy, and no hardcoded preferred frontier model.

Profile instructions are meaningful guidance, but only schema fields and controller/evaluator checks are mechanically enforced. Every claim of enforcement should point to code and a negative regression test. Narrative governance must not masquerade as an executable guarantee.

## New interventions require new evidence

An improved parser, better browser tool, revised prompt and different model are separate interventions. Change one at a time initially. Preserve a fixed baseline and independently owned acceptance. Re-evaluate useful scaffolding when models change; yesterday's workaround can become tomorrow's overhead.
